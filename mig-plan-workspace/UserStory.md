# User Stories: Coolstore → Quarkus 3.15 / Java 21 on OpenShift

> Generated by **mig-plan** (MigIQ Phase 3). Each story links to task groups in [`tasks.md`](tasks.md).
> Spec and design: [`../mig-prompt-workspace/migration-prompt.md`](../mig-prompt-workspace/migration-prompt.md).

## User Story 1: Capture Current Behaviour Before Changing It

**As a:** Migration Developer
**I want:** Automated tests that record today's pricing, promotion, shipping and JSON behaviour
**So that:** I can prove the Quarkus version behaves the same as the old one

---

### Tasks
- [## Task Group 1: Baseline & Characterization Tests](tasks.md#task-group-1-baseline--characterization-tests)

### Acceptance Criteria
- [ ] Tag `pre-quarkus-migration` exists and the migration branch is created
- [ ] Golden data is recorded for the ShippingService tiers, the PromoService rules (329299 −25%, free shipping ≥ $75) and the cart totals
- [ ] The REST JSON contract (field names for Product, ShoppingCart, Order) is written down
- [ ] The characterization tests are plain JUnit 5 and do not depend on a container

---

### Details
- **Priority:** High
- **Estimate:** 2 SP

---

### Preconditions
- Repository at the current legacy state. rgctl index and Konveyor analysis are available.

---

### Steps to Reproduce / Implementation Notes
1. Tag the repo and record the baseline (1.1–1.2)
2. Extract the golden data and the contract (1.3–1.5)
3. Generate the tests with mig-test-gen (1.6)

---

### Dependencies
- None

---

### Test Cases
- Test 1: Cart with item 329299 → its price is reduced by 25%
- Test 2: Cart subtotal $75.00 → shipping is 0. At $74.99 the tiered shipping rate applies.
- Test 3: `Transformers.jsonToOrder(sample)` → the Order fields match the fixture

---

### Notes / Comments
- The tests must keep passing unchanged after Groups 3–6. This is the main regression guard for the big-bang approach.

## User Story 2: Run on a Modern, Supported Runtime with Managed Schema

**As a:** Platform Engineer
**I want:** The application to build on Java 21 and Quarkus 3.15 LTS, with Hibernate ORM and Flyway managed by Quarkus
**So that:** We leave the end-of-life Java EE 7 / Java 8 stack and the database schema is created on every start in each environment

---

### Tasks
- [## Task Group 2: Build Foundation](tasks.md#task-group-2-build-foundation-quarkus-315-lts-java-21-audit-logging-library-200)
- [## Task Group 3: Model & Persistence](tasks.md#task-group-3-model--persistence-jpa-flyway-datasource)

### Acceptance Criteria
- [ ] `pom.xml` uses the Quarkus 3.15.x BOM, `release 21` and jar packaging. No Java EE API dependencies remain.
- [ ] audit-logging-library 2.0.0 resolves (installed locally or system scope). Version 1.0.0 is removed.
- [ ] `persistence.xml`, `Resources` and `DataBaseMigrationStartup` are deleted. Flyway applies V1_1/V1_2 at start on H2 (dev/test).
- [ ] The prod profile points to PostgreSQL through environment variables. No credentials are committed.

---

### Details
- **Priority:** High
- **Estimate:** 3 SP

---

### Preconditions
- Story 1 done. JDK 21 and Maven available (`/tmp/jdk`, `/tmp/mvn`). Maven Central reachable.

---

### Steps to Reproduce / Implementation Notes
1. Rewrite the POM and add the extensions (2.1–2.2)
2. Inspect and install the audit jar (2.3–2.4)
3. Write `application.properties` and migrate the JPA entities to jakarta (2.5, 3.1–3.5)

---

### Dependencies
- User Story 1

---

### Test Cases
- Test 1: `@QuarkusTest` startup → Flyway history shows V1_1, V1_2 and the catalog rows are present
- Test 2: Persist an Order with OrderItems → reading it back returns the same data

---

### Notes / Comments
- Risk R5: the SQL scripts may need a V1_3 compatibility script for PostgreSQL. Never edit scripts that have already been applied.

## User Story 3: Stateless, Cloud-Ready Business Services with Streamed Audit Logs

**As a:** Platform Engineer
**I want:** EJBs replaced by CDI beans, the ShippingService injected instead of looked up in JNDI, carts kept in an application-scoped store, and audit events streamed over TCP
**So that:** Pods can restart and scale on OpenShift without server-specific features or local audit files

---

### Tasks
- [## Task Group 4: Services: EJB → CDI, ShippingService Injection, Cart Store, Audit Logging 2.0.0](tasks.md#task-group-4-services-ejb--cdi-shippingservice-injection-cart-store-audit-logging-200)

### Acceptance Criteria
- [ ] No `javax.ejb`, `InitialContext` or `ShippingServiceRemote` remains in the code
- [ ] `CartStore` keeps carts by cartId, and two cartIds never see each other's items
- [ ] `OrderService` uses `StreamableAuditLogger` (TCP), constructs `new AuditEvent(...)` and calls `logEventAsync`, with no builder, `logEvent`, `logSuccess` or `logFailure` (rules audit-logging-0002…0005)
- [ ] Checkout still succeeds when the audit collector cannot be reached
- [ ] The Story 1 characterization tests pass

---

### Details
- **Priority:** High
- **Estimate:** 3 SP

---

### Preconditions
- Story 2 done, and the audit 2.0.0 API is documented (task 2.3)

---

### Steps to Reproduce / Implementation Notes
1. Convert the stateless services and inject ShippingService (4.1–4.2)
2. Introduce CartStore and refactor ShoppingCartService (4.3–4.4)
3. Migrate audit logging to 2.0.0 (4.5) and run the grep check (4.6)

---

### Dependencies
- User Story 2

---

### Test Cases
- Test 1: Concurrent adds to the same cartId → quantities are correct
- Test 2: A local TCP listener receives an AuditEvent after `OrderService.save`
- Test 3: The collector is down → save commits and a warning is logged

---

### Notes / Comments
- Risk R2: carts live in memory per pod, so the Route uses sticky sessions. Data Grid/Redis is a follow-up.

## User Story 4: Reliable Order Processing via Reactive Messaging

**As a:** Store Operator
**I want:** Checkout to publish orders on a reactive messaging channel that persists them
**So that:** Orders are still recorded without a JMS server or a WebLogic connection

---

### Tasks
- [## Task Group 5: Messaging: JMS/MDB/WebLogic → SmallRye Reactive Messaging](tasks.md#task-group-5-messaging-jmsmdbweblogic--smallrye-reactive-messaging)

### Acceptance Criteria
- [ ] `ShoppingCartOrderProcessor` sends to the `orders` Emitter, and an `@Incoming("orders")` consumer persists the Order in a transaction
- [ ] `InventoryNotificationMDB` is an `@Incoming("inventory")` consumer, with no t3 JNDI
- [ ] The `weblogic.*` stubs and `StartupListener` are deleted. Lifecycle code uses `StartupEvent`/`ShutdownEvent`.
- [ ] The default is in-memory with no broker. The AMQP profile is documented.

---

### Details
- **Priority:** High
- **Estimate:** 2 SP

---

### Preconditions
- Story 3 done (OrderService is transactional CDI)

---

### Steps to Reproduce / Implementation Notes
1. Replace the producer and consumer (5.1–5.3)
2. Delete the WebLogic code (5.4), configure the channels (5.5), run the grep check (5.6)

---

### Dependencies
- User Story 3

---

### Test Cases
- Test 1: Emit cart JSON → within 5 s the Order exists in the DB (Awaitility)
- Test 2: Send an inventory message → the consumer logs the notification without errors

---

### Notes / Comments
- Risk R3: in-memory delivery is not durable. This is accepted for now.
