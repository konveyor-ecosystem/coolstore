# User Stories: CoolStore → Quarkus 3.15 / Java 21 on OpenShift

> Generated by mig-plan (MigIQ Phase 3). Each story links to task groups in `tasks.md`. Design decisions are in `mig-prompt-workspace/migration-prompt.md` (D1-D13).

## User Story 1: Safety Net and Build Foundation

**As a:** developer on the migration team
**I want:** contract tests that capture today's API behaviour, plus a Quarkus 3.15 / Java 21 build that passes in CI
**So that:** we can change the whole app at once and know straight away if something breaks

---

### Tasks
- Task Group 1: Characterization Baseline & Safety Net
- Task Group 2: Build Foundation (Quarkus 3.15 BOM, Java 21, audit-logging 2.0.0)

### Acceptance Criteria
- [ ] `docs/api-contract.md` lists all 10 `/services` operations with golden JSON fixtures
- [ ] Unit tests for ShippingService tiers, PromoService and Transformers exist and pass
- [ ] CI runs `mvn -B verify` on Java 21 and passes; the stale Azure workflow has been removed
- [ ] `pom.xml` has no Java EE 7, JMS, RMI or Flyway 4 dependencies and uses audit-logging-library 2.0.0 (not system scope)

---

### Details
- **Priority:** High
- **Estimate:** 5 story points

---

### Preconditions
- Migration prompt approved; CI runner with Java 21 and Maven available (the sandbox has neither)

---

### Steps to Reproduce / Implementation Notes
1. Write the contract docs and fixtures (TG1), then generate tests with mig-test-gen.
2. Rewrite the pom and properties (TG2) and get the first green CI build.

---

### Dependencies
- None (first story)

---

### Test Cases
- Test 1: Shipping for cart total 24.99 → 2.99; 25.00 → 4.99 plus 2% insurance
- Test 2: The `@QuarkusTest` boot test reports `/q/health` UP

---

### Notes / Comments
- The EAP app cannot be run here, so the characterization tests come from the code and spec. Review them against a running EAP instance if one is available.

---

## User Story 2: Data and Core Services on Quarkus

**As a:** shopper
**I want:** the product catalogue and inventory to load from the same PostgreSQL database
**So that:** I see the same products and stock after the platform change

---

### Tasks
- Task Group 3: Persistence, Namespaces & EJB → CDI Core

### Acceptance Criteria
- [ ] No `javax.*` Java EE imports remain; EJBs are replaced by CDI beans with `@Transactional`
- [ ] Quarkus Flyway applies V1_1/V1_2 on an empty DB and baselines an existing DB without errors
- [ ] `GET /services/products` returns the seeded catalogue matching the golden JSON
- [ ] Order IDs come from `hibernate_sequence`; the dangling `TOTAL_PRICE` mapping is removed

---

### Details
- **Priority:** High
- **Estimate:** 5 story points

---

### Preconditions
- Story 1 complete (green build)

---

### Steps to Reproduce / Implementation Notes
1. Run the jakarta migration, delete persistence.xml and Resources, and convert the services.
2. Configure the datasource and Flyway, then add Dev Services tests.

---

### Dependencies
- User Story 1

---

### Test Cases
- Test 1: Dev Services DB: product count equals the number of seed rows
- Test 2: Persisting an Order with 2 items gives ids from the sequence and saves the items

---

### Notes / Comments
- Risk: the Flyway 4 history table differs (`schema_version`). Mitigated by `quarkus.flyway.table` and a baseline.

## User Story 3: Shopping Cart and Asynchronous Checkout

**As a:** shopper
**I want:** to add, update and remove cart items and check out exactly as before
**So that:** my order is placed and stock is reduced without me noticing any change

---

### Tasks
- Task Group 4: Messaging: JMS/MDB → SmallRye Reactive Messaging
- Task Group 5: Shipping Service & Cart State

### Acceptance Criteria
- [ ] Checkout sends the cart JSON on the `orders` channel (in-memory); the consumer saves the Order and decrements inventory in one transaction
- [ ] The AMQP profile is documented and switches the connector by configuration only
- [ ] ShippingService is a local CDI bean; the code has no JNDI or `@Remote`
- [ ] Carts are keyed by `cartId` in `CartStore`; two `cartId`s stay isolated; `<distributable/>` is removed (Konveyor session-00000 resolved)
- [ ] All `/services/cart/*` contract tests pass

---

### Details
- **Priority:** High
- **Estimate:** 8 story points

---

### Preconditions
- Story 2 complete

---

### Steps to Reproduce / Implementation Notes
1. Use an Emitter in place of the JMSContext producer, and an `@Incoming` consumer in place of the MDB; delete InventoryNotificationMDB.
2. Inject ShippingService and add CartStore with an in-memory implementation; make the endpoint stateless.
3. Run InMemoryConnector and REST tests.

---

### Dependencies
- User Story 2

---

### Test Cases
- Test 1: Add item, then checkout → the order shows up in `GET /services/orders` (awaitility)
- Test 2: A malformed message is logged and does not crash the consumer

---

### Notes / Comments
- In-memory messaging is not durable (JMS was), so in-flight orders are lost if a pod crashes. This is accepted for moderate risk tolerance; AMQP is the upgrade path.
- Cart state is held per pod, so the Route uses sticky sessions. A shared store (Data Grid/Redis) is a follow-up item.

---

## User Story 4: Compliant Audit Trail

**As a:** compliance officer
**I want:** every saved order to send an audit event to the central audit collector, using audit-logging-library 2.0.0
**So that:** audit records survive container restarts and meet the company standard

---

### Tasks
- Task Group 6: Audit Logging 2.0.0 (Konveyor rules audit-logging-0001 to 0005)

### Acceptance Criteria
- [ ] `StreamableAuditLogger` (TCP) replaces `FileSystemAuditLogger`; every event is a full `AuditEvent` record sent with `logEventAsync`
- [ ] Re-running the Konveyor custom rules reports 0 incidents for audit-logging-0001..0005
- [ ] An unreachable or disabled collector never makes order saving fail

---

### Details
- **Priority:** Medium
- **Estimate:** 3 story points

---

### Preconditions
- Story 2 complete; host/port of the audit collector known (or the feature flag is off)

---

### Steps to Reproduce / Implementation Notes
1. Check the API with javap, then write the producer, then add the record plus async call in OrderService.save.
2. Add fake TCP server tests.

---

### Dependencies
- User Story 2

---

### Test Cases
- Test 1: The fake TCP server receives the JSON event with `action`, `resource` and `result`
- Test 2: Collector down → the order is still persisted and a warning is logged

---

### Notes / Comments
- The API details were inferred from the bytecode only (Java 21 class files), so they must be confirmed in CI.

---

## User Story 5: Unchanged Storefront and Optional SSO

**As a:** shopper
**I want:** the same AngularJS storefront and Keycloak login, served by the new application
**So that:** nothing changes for me when the platform changes

---

### Tasks
- Task Group 7: REST Layer, Front End, Auth & Legacy Cleanup

### Acceptance Criteria
- [ ] `/` serves the storefront; all `/services/products|cart|orders` contract tests pass
- [ ] `keycloak.json`/`coolstore.json` come from a ConfigMap; `SSO_ENABLED=false` works with no Keycloak present
- [ ] `quarkus-oidc` is included but disabled by default; the steps to protect `/services/orders` are documented

---

### Details
- **Priority:** High
- **Estimate:** 5 story points

---

### Preconditions
- Stories 2-3 complete

---

### Steps to Reproduce / Implementation Notes

2. Externalise the auth config and delete legacy classes.

---

### Dependencies
- User Stories 2, 3

---

### Test Cases
- Test 1: GET `/` → 200 and the HTML contains the Angular app bootstrap
- Test 2: `/q/health/ready` → UP when the DB is reachable

---

### Notes / Comments

## User Story 6: Run CoolStore on OpenShift

**As a:** platform engineer
**I want:** a scanned UBI-based container image and Kustomize manifests for OpenShift
**So that:** I can deploy CoolStore repeatably with health checks, config and secrets

---

### Tasks
- Task Group 8: Containerization (UBI 9, Java 21)
- Task Group 9: OpenShift Deployment Manifests

### Acceptance Criteria
- [ ] The multi-stage Containerfile (ubi9/openjdk-21 → openjdk-21-runtime) builds in CI and runs as non-root on port 8080
- [ ] The image scan shows no critical CVEs
- [ ] `kustomize build` for the dev/prod overlays passes kubeconform; the manifests include Deployment, Service, Route, ConfigMaps, a Secret template, PostgreSQL, PDB, HPA, NetworkPolicy and ServiceMonitor
- [ ] On a cluster, the pod becomes Ready and the E2E checkout script passes through the Route

---

### Details
- **Priority:** High
- **Estimate:** 5 story points

---

### Preconditions
- Stories 1-5 complete; access to an OpenShift project and a registry

---

### Steps to Reproduce / Implementation Notes
1. Use mig-containerize to produce the Containerfile and add the CI image build and scan.
2. Use mig-deploy to produce the base and overlays, then validate statically and apply in dev.

---

### Dependencies
- User Stories 1-5

---

### Test Cases
- Test 1: The `@QuarkusIntegrationTest` against the image passes
- Test 2: Load test, 50 VU: p95 < 300 ms

---

### Notes / Comments
- The sandbox has no container engine or `oc`, so the image build and deployment are validated in CI or on the cluster.

## User Story 7: Safe Cutover and Rollback

**As a:** product owner
**I want:** a rehearsed cutover lasting no more than 15 minutes, with monitoring and a tested rollback to EAP
**So that:** the business takes little risk when we switch platforms

---

### Tasks
- Task Group 10: Cutover, Observability & Rollback

### Acceptance Criteria
- [ ] Metrics, alerts and JSON logs are live in OpenShift monitoring
- [ ] The Flyway baseline dry run on a copy of the production DB succeeds
- [ ] The cutover and rollback runbooks have been rehearsed in a staging environment
- [ ] Konveyor and rgctl re-analysis show 0 mandatory incidents; coverage is at least 80%

---

### Details
- **Priority:** Medium
- **Estimate:** 3 story points

---

### Preconditions
- Story 6 deployed to staging

---

### Steps to Reproduce / Implementation Notes
1. Set up observability, then do the data dry run, then rehearse.
2. Cut over in a maintenance window, monitor for 48 h, then decommission EAP after 30 days.

---

### Dependencies
- User Story 6

---

### Test Cases
- Test 1: The post-cutover regression suite passes against prod
- Test 2: Rollback drill: switching the Route back to EAP takes less than 5 minutes

---

### Notes / Comments
- Drain the in-flight JMS orders on EAP before the cutover.
